## 4. Співпраця та робочий процес
- Стратегія гілкування: GitHub Flow
- Практики комітів: гранулярно, формат лаконічний
- **Робочий процес завдань**:
  1. **Відкрити**: створення Issue в GitHub за шаблоном (`[TASK]`, `[BUG]`), фіксація суті задачі та критеріїв прийнятності (Acceptance Criteria).
  2. **Призначити**: призначення виконавця (Assignee) та виставлення відповідних міток (Labels: `enhancement`, `documentation`, тощо).
  3. **Працювати**: створення тематичної гілки від `main` (`feature/...`, `docs/...`), гранулярні коміти з лаконічним описом та обов'язкова самоперевірка автором.
  4. **PR (Pull Request)**: відкриття PR у гілку `main` із лінком на Issue (`Closes #XX`), успішний білд у CI та проходження рев'ю (мінімум 1 схвалення).
  5. **Закрити**: злиття PR у `main`, автоматичне закриття пов'язаного Issue та видалення робочої гілки.

- **Власні мітки трекера** (описи збігаються з налаштуваннями міток у GitHub):

  | Мітка | Призначення |
  | :--- | :--- |
  | `To do before Lab N` (N = 2…14) | задача, яку обов'язково треба зробити за 24 години до вказаної практики |
  | `feedback` | зворотний звʼязок викладача; не входить в оцінку трекера |
  | `Fix` | виправлення бага чи помилки |

  Мітки `bug`, `enhancement`, `documentation`, `question` тощо — стандартний набір GitHub, використовуються без змін.

- **Означення готовності завдання (Definition of Done)**: завдання вважається готовим, якщо виконано всі пункти:
  1. Виконано всі критерії прийнятності (Acceptance Criteria) з Issue.
  2. Створено тематичну гілку від актуального `main`, зміни закомічено гранулярно з лаконічним описом.
  3. Автор провів самоперевірку (логіка, граничні випадки, відсутність сміття/тестових артефактів).
  4. Відкрито PR у `main` з лінком на Issue (`Closes #XX`).
  5. Білд CI зелений.
  6. Отримано мінімум 1 схвалення від іншого учасника; всі зауваження рев'ю закрито або адресовано.
  7. Оновлено пов'язану документацію; за наявності внеску ШІ додано нотатку за форматом §8.
  8. PR злито в `main`, Issue закрито автоматично, робочу гілку видалено.
- **Огляд користувацьких історій**: обов'язковий PR у `main` та мінімум 1 схвалення, перевірка критеріїв прийняття (Given-When-Then) та критеріїв INVEST.
- **Перевірка NFR**: Написання основним автором і групове обговорення в групі та на PR.
- **Управління артефактами вимог**: усі документи зберігаються виключно в каталозі `/docs/requirements/` (`requirements.md`, `user-stories.md`, `rtm.md`); обов'язок керівника документації — підтримувати актуальні посилання на них у `README.md`.
- **Індивідуальна відповідальність (Loom-звітність)**: кожен учасник записує відео (≤5 хв) з показом свого внеску (US, NFR чи RTM).

## 8. Використання ШІ
* **Інструменти**: Google Gemini, Antigravity, Claude Code, OpenCode / GitHub Copilot
* **Правила розкриття**:
  * Загальний опис сфер застосування ШІ фіксується у документації проєкту.
  * У разі створення значної частини модуля чи функції за допомогою ШІ робиться відповідна примітка в описі Pull Request або коментарем у коді.
* **Правило верифікації**:
  * Увесь згенерований або запропонований ШІ код підлягає обов'язковій ручній перевірці автором, компіляції та тестуванню на граничних випадках. Сліпе додавання неперевіреного коду заборонено.
* **Формат нотатки** (додається до кожного артефакту, створеного або редагованого з ШІ):
  * **Документація** — таблиця `| Об'єкт | Внесок | ШІ | Як перевірено |`, **рядок на внесок**: для вимог — на одиницю (`US-###`, `FR-###`, `NFR`), у документі — на зачеплену частину.
  * **Код** — коментар на початку файлу: `AI: <що згенеровано>; перевірено: <механізм>`.
  * Інструмент ШІ в нотатці не вказується — перелік інструментів вище.
  * Рядок дописують, чужий не переписують. «Як перевірено» називає механізм (рев'ю, підпис, обговорення, тести, CI), а не оцінку.
