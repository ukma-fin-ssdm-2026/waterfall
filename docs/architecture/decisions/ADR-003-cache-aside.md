# ADR-003: Cache-Aside In-Memory кеш каталогу

- Статус: прийнято
- Дата: 2026-09-27
- Автор рішення: Дмитро

## Контекст

PERF-001: сторінка 20 вакансій <1 с p95 при 10k записів. Прямі запити в DB на кожну фільтрацію не вкладаються.

## Рішення

Читання `Storage → Cache → DB` з TTL та інвалідацією при надходженні нових вакансій (§3.3.2, §3.4.2). Агреговані аналітичні звіти кешуються, персональні рекомендації — ні (FR-006, on-demand ранжування).

## Розглянуті альтернативи

- **Redis (розподілений кеш).** Відхилено: в одному процесі In-Memory дає ті ж p95 <1 с без мережевих хопів, окремого сервісу й операцій; Redis стане потрібен лише при горизонтальному масштабуванні (кілька інстансів API) — тоді ключ кешу вже містить `user_id`/фільтри (THR-07), тож міграція не ламає контракт.
- **Без кешу (прямі запити в DB на кожну фільтрацію).** Відхилено: не вкладається в PERF-001 — сторінка 20 вакансій з 10k записів має віддаватися <1 с p95 при 100 одночасних користувачах; DB лишається джерелом правди, кеш лише прискорює читання (запис збережень синхронний, REL-002), а за зриву оновлення каталог деградує до stale-cache ≤12 год (REL-001).

## Наслідки

+ Каталог p95 <1 с; REL-001: за недоступності джерела — stale-cache ≤12 год з міткою часу.
− Волатильність при рестарті (прийнято: прогрів з DB; запис збережень синхронний, REL-002).
