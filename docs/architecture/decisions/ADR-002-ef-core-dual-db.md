# ADR-002: MSSQL + SQLite через EF Core

- Статус: прийнято
- Дата: 2026-09-27
- Автор рішення: Данило

## Контекст

Продакшн потребує серверної СУБД, локальна розробка/демо — zero-setup. Два діалекти без ORM = подвійні запити.

## Рішення

EF Core репозиторії (§3.4.3); MSSQL на сервері (TDS/TCP), SQLite локально (файл). Типи атрибутів абстрактні (`uuid`, `json`, `enum` як рядок), мапінг на діалект — на рівні провайдера. Сутності з ідентифікаторами в API (`User`, `UserSession`, `ChatSession`) мають PK `uuid`, щоб унеможливити перебір записів інкрементом.

## Розглянуті альтернативи

- **PostgreSQL як єдина СУБД (сервер + локально).** Відхилено: команда працює в стеку MSSQL/SQLite (курс, наявні ліцензії/інструменти), а zero-setup демо на SQLite-файлі простіше за підняття Postgres; виграш (full-text пошук, JSONB) на масштабі 10k записів не окупає зміну стеку.
- **Лише MSSQL (без SQLite).** Відхилено: локальна розробка/демо вимагали б живого сервера; dual-provider через EF Core дає один код доступу ціною мапінгу діалектів на рівні провайдера.
- **Dapper / raw SQL без ORM.** Відхилено: два діалекти без ORM = подвійні запити й ручний мапінг; EF Core покриває пагінацію/міграції з коробки, а складений ключ `SavedVacancy(user_id, vacancy_id)` працює в обох СУБД без специфічного SQL.

## Наслідки

+ Один код доступу, складений ключ `SavedVacancy(user_id, vacancy_id)` працює в обох СУБД.
− Без специфічних фіч MSSQL (full-text пошук — зарезервовано).
