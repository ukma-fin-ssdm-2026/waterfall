# Журнал налагодження

**Помилка:** домен-двійник проходить перевірку посилання на вакансію  
**Модуль:** збір вакансій, [`VacancyIngestionService.NormalizeUrl`](../../src/waterfall.Services/VacancyIngestionService.cs) (issue #62)  
**Як з'явилася:** внесена навмисно на практиці «Зламай, потім відлагодь» (Lab 06), щоб перевірити, чи її впіймають тести

## Симптом

Вакансія з посиланням `https://fakedjinni.co/jobs/1/` проходила нормалізацію й зберігалася як вакансія з Djinni. Шахрайська вакансія з фішинговим посиланням потрапила б у каталог під виглядом справжньої — саме від цього захищає перевірка (загроза THR-03). Набір тестів модуля при цьому лишався зеленим:

```text
Passed!  - Failed: 0, Passed: 27
```

## Причина

З перевірки піддомену зникла крапка:

```csharp
// правильно: сам djinni.co або його піддомен (jobs.djinni.co)
uri.Host == SourceHost || uri.Host.EndsWith("." + SourceHost, StringComparison.Ordinal)
// з помилкою: будь-який домен, що закінчується літерами «djinni.co»
uri.Host == SourceHost || uri.Host.EndsWith(SourceHost, StringComparison.Ordinal)
```

Тести мовчали, бо жодне «погане» посилання в них (`djinni-careers.example.net`, `djinni.co.evil.example`, `http://djinni.co`) не закінчується на `djinni.co`. Умову, яку зламала помилка, не перевіряв жоден тест.

Як шукали:
1. **Відтворили.** Тести зелені, тож відтворили новим тестом із `fakedjinni.co`, і він упав.
2. **Ізолювали.** Падав лише цей випадок; повідомлення показало, що `Normalize` повернув вакансію там, де мав повернути `null`.
3. **Діагностували.** Причина знайшлася в `NormalizeUrl`, в умові `fromSource`: суфікс без крапки.

## Виправлення

Повернули `"." + SourceHost`. Регресійний тест — випадок `fakedjinni.co` у `Normalize_RejectsLinksOutsideDjinni` ([VacancyIngestionServiceTests.cs, рядок 100](../../tests/waterfall.Ingestion.Tests/VacancyIngestionServiceTests.cs#L100)). З помилкою він падає:

```text
Failed Normalize_RejectsLinksOutsideDjinni(url: "https://fakedjinni.co/jobs/1/")
  Assert.Null() Failure: Value is not null
Failed!  - Failed: 1, Passed: 45, Total: 46
```

Після виправлення проходять усі 46. Щоб виправлення не відрізало справжні піддомени, поруч є позитивний тест `Normalize_AcceptsDjinniSubdomain` (`jobs.djinni.co` приймається).

## Урок

- Перевірки на кшталт «закінчується на» чи «починається з» треба тестувати на самій межі: домен-двійник із тим самим закінченням (`fakedjinni.co`), а поруч справжній піддомен (`jobs.djinni.co`).
- Зелені тести ще не означають захищений код. Тести мають атакувати умову, а не лише підтверджувати очевидні випадки. З 15 помилок, навмисно внесених на практиці в усі модулі, тести пропустили 4.
- Наступного разу для коду, що стосується безпеки, одразу вносити помилки навмисно й дивитися, чи впаде хоч один тест. Це дешевий спосіб знайти такі прогалини ще до того, як ними скористається хтось інший.

## Кейс 2. Витік чужих закладок між користувачами через спільний кеш каталогу

**Модуль:** бізнес-сервіс вакансій, [`VacancyService.GetAllAsync`](../../src/waterfall.Services/VacancyService.cs#L92)  
**Автор налагодження:** Сидоренко Денис  
**Як з'явилася:** внесена навмисно на практиці «Зламай, потім відлагодь» (Lab 06), щоб перевірити, чи її впіймають тести

### Симптом

Користувач А відкриває каталог вакансій, де одна з вакансій збережена в нього в «Обране» (`IsSaved = true`). Якщо після нього Користувач Б відкриває ту саму сторінку каталогу під своїм акаунтом, він теж бачить цю вакансію як збережену. Відбувається витік чужих персональних закладок через спільний кеш у пам'яті.

Набір тестів модуля без нового тесту лишався зеленим:

```text
Passed!  - Failed: 0, Passed: 34
```

### Причина

Перед тим як покласти сторінку вакансій у спільний кеш, прибрали перевірку `if (userId is null)`:

```csharp
// правильно: у спільний кеш кладемо лише сторінки без персональних закладок конкретного користувача
if (userId is null)
{
    await _cacheService.SetPagedVacanciesAsync(filter, result, null, ct);
}

// з помилкою: сторінка із закладками Користувача А полетіла в загальний кеш для всіх інших користувачів
await _cacheService.SetPagedVacanciesAsync(filter, result, null, ct);
```

Старі тести перевіряли роботу кешу лише для базового виклику каталогу без передачі ID користувача (`userId: null`), тому ніхто не перевіряв, чи не засмічує кеш запит конкретного користувача з його прапорцями.

Як шукали:
1. **Відтворили.** Написали тест із передачею `userId` користувача із закладкою і перевірили стан кешу після запиту — він виявився не порожнім, тест упав із `Assert.Empty() Failure`.
2. **Ізолювали.** Падав саме цей тест на перевірці порожнечі кешу після виклику `GetAllAsync`.
3. **Діагностували.** Помилка була в кінці методу `GetAllAsync` — запис у кеш викликався наосліп без перевірки `userId is null`.

### Виправлення

Повернули умову `if (userId is null)`. Регресійний тест — [`GetAllAsync_AuthenticatedUser_BypassesCacheAndEnrichesIsSavedFlags`](../../tests/waterfall.Services.Tests/VacancyServiceTests.cs#L117) у [`VacancyServiceTests.cs`](../../tests/waterfall.Services.Tests/VacancyServiceTests.cs). З помилкою він падає:

```text
Failed GetAllAsync_AuthenticatedUser_BypassesCacheAndEnrichesIsSavedFlags
  Assert.Empty() Failure: Collection was not empty
Failed!  - Failed: 1, Passed: 34, Total: 35
```

Після повернення перевірки проходять усі 35 тестів.

### Урок

- У загальний кеш не можна зберігати відповіді з персональними даними конкретного користувача (лайки, збережені вакансії тощо).
- Тести для кешу мають перевіряти не лише те, що дані збереглися (Happy Path), а й що при запитах з прив'язкою до конкретного користувача спільний кеш лишається порожнім (`Assert.Empty(cache)`).
