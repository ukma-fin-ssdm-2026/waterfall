# Атрибути якості API Waterfall

Кожна ціль нижче має чотири частини: **число**, **умову, за якої ціль вважається проваленою**, спосіб реалізації та спосіб вимірювання. Ціль, яка не може провалитися, нічого не вимірює. Категорії взято з моделі ISO/IEC 25010, а цілі прив'язано до нефункціональних вимог з [requirements.md](../requirements/requirements.md).

## 1. Продуктивність

### P-1. Сторінка каталогу

- **Ціль:** `GET /api/v1/vacancies?pageSize=20` відповідає за p95 < 1000 мс при 50 одночасних користувачах і базі щонайменше з 10 000 вакансій (PERF-001).
- **Умова провалу:** p95 ≥ 1000 мс **або** понад 5% відповідей зі статусом 5xx у п'ятихвилинному прогоні.
- **Реалізація:**
  - пагінація з обмеженням `pageSize` ≤ 100 (реалізовано);
  - фільтрація й пошук на сервері, клієнт отримує лише одну сторінку (реалізовано);
  - кешування сторінок каталогу в `VacancyCacheService` за патерном Cache-Aside у пам'яті, час життя запису 10–15 хвилин (реалізовано).
- **Вимірювання (заплановано):** навантажувальний тест k6: 50 віртуальних користувачів, 5 хвилин, пороги `http_req_duration p(95) < 1000` і `http_req_failed rate < 0.05`. Скрипт ще не написано: прогін має сенс лише після заповнення БД щонайменше 10 000 вакансій, а сідер зараз додає 5.

### P-2. Деталі вакансії

- **Ціль:** `GET /api/v1/vacancies/{id}` відповідає за p95 < 300 мс за тих самих умов.
- **Умова провалу:** p95 ≥ 300 мс або понад 1% відповідей 5xx.
- **Реалізація:** пошук за первинним ключем, без фільтрації та сортування.
- **Вимірювання (заплановано):** окремий сценарій у тому самому тесті k6. Запити йдуть лише до наявних id: k6 зараховує 404 до невдалих запитів, тож випадкові id спотворили б частку помилок.

## 2. Надійність

### R-1. Некоректні дані не призводять до збою

- **Ціль:** 0 відповідей 5xx на наборі негативних тест-кейсів із розділу 6.
- **Умова провалу:** хоча б одна відповідь 5xx.
- **Реалізація:**
  - валідація атрибутами DTO та `IValidatableObject` на всіх кінцевих точках, де є вхідні дані;
  - єдина фабрика `InvalidModelStateResponseFactory`, яка перетворює будь-яку помилку валідації на 400;
  - виправлені випадки, що раніше завершувалися 500 (розділ 7).
- **Вимірювання:** ручний прогін розділу 6 через Swagger UI; надалі — автоматичні інтеграційні тести в CI.

### R-2. Відмова LLM не ламає API

- **Ціль:** за недоступності LLM API або вичерпання ліміту безкоштовного тарифу клієнт не пізніше ніж за 30 с отримує відповідь `503` з кодом `LLM_UNAVAILABLE` і пропозицією скористатися звичайним пошуком (REL-003).
- **Умова провалу:** очікування відповіді понад 30 с **або** відповідь 500.
- **Реалізація:** таймаут HTTP-клієнта до LLM — 30 с; помилки провайдера перехоплюються в `AI Consultant Service` і перетворюються на 503 у єдиному форматі помилок. Ендпоінт ШІ-консультанта ще не реалізовано, тож ціль закладено наперед.
- **Вимірювання (заплановано разом з ендпоінтом):** інтеграційний тест, у якому клієнт LLM підмінено заглушкою, що імітує таймаут або відповідь `429`.

## 3. Безпека

### S-1. Невалідний вхід завжди відхиляється

- **Ціль:** кожен запит з невалідними даними отримує `400 Bad Request` з кодом `VALIDATION_ERROR` і списком `details`, де вказано поле та причину. Жодного 5xx. Єдиний свідомий виняток — `page` і `pageSize` за нижніми межами: сервер виправляє їх на допустимі значення (розділ 4).
- **Умова провалу:** будь-який кейс із розділу 6 повертає інший статус, ніж очікується, або 5xx, **або** тіло відповіді містить внутрішні деталі: назви типів .NET, стек викликів, номери рядків.
- **Реалізація:**
  - **Валідація діапазонів** — повний перелік правил у таблиці нижче.
  - **Санітизація вхідних даних:** сервіс обрізає пробіли на краях рядків; валюта приймається лише з переліку `USD`, `EUR`, `UAH`; довжина кожного рядка й розмір кожного списку обмежені. Тексти зберігаються й повертаються як дані: клієнт .NET MAUI показує їх як текст, а не як розмітку.
  - **Приховування внутрішнього стану:** `AllowInputFormatterExceptionMessages = false`, тож текст винятків десеріалізатора не потрапляє до клієнта; замість нього повертається «Некоректне значення або формат поля».
  - **Заплановано:** обмеження частоти (100 запитів на хвилину з однієї IP-адреси), JWT для `/saved-vacancies`, лише HTTPS у продакшні.
- **Вимірювання:** прогін розділу 6; надалі — статичний аналізатор безпеки для C# і перевірка вразливих залежностей (`dotnet list package --vulnerable`) у Лабораторній 5.

| Поле або параметр | Правило |
| --- | --- |
| `page` | ціле, до 100 000; значення менше 1 замінюється на 1 |
| `pageSize` | ціле; менше 1 замінюється на 10, більше 100 — на 100 |
| `search`, `category`, `experience` (query) | до 100 символів |
| `minSalary`, `maxSalary` | 0–1 000 000; `minSalary` ≤ `maxSalary` |
| `source` (query) | одне з `WorkUa`, `RobotaUa`, `Djinni`, `Dou` |
| `title` | 3–200 символів |
| `company` | 2–200 символів |
| `description` | 10–10 000 символів |
| `category` (тіло) | до 100 символів |
| `location` | до 200 символів |
| `fullAddress`, `schedule`, `experience` (тіло) | до 300, 100 і 100 символів |
| `salaryMin`, `salaryMax` | 0–1 000 000; `salaryMin` ≤ `salaryMax` |
| `currency` | `USD`, `EUR` або `UAH` |
| `source` (тіло) | `WorkUa`, `RobotaUa`, `Djinni` або `Dou`; `Unknown` і числа поза переліком відхиляються |
| `sourceUrl` | дійсний URL до 2048 символів |
| `skills` | до 30 елементів, кожен до 50 символів; порожні навички допускаються, але не потрапляють під пошук |
| `vacancyId` | обов'язковий, непорожній GUID |
| `notes` | до 500 символів |
| `{id}` у шляху | GUID |

Під час створення вакансії (`POST`) поля `title`, `company`, `description`, `category`, `location`, `currency`, `source` і `sourceUrl` обов'язкові. У `PUT` усі поля необов'язкові: відсутнє поле або `null` означає «не змінювати», а правила з таблиці діють для переданих значень.

## 4. Компроміси

| Атрибут | Компроміс | Вплив | Пом'якшення |
| --- | --- | --- | --- |
| Продуктивність ↔ свіжість даних (кешування) | Кеш сторінок каталогу пришвидшує відповідь, але користувач може побачити вакансію, яку вже закрили, або не побачити щойно зібрану | Розбіжність із джерелом у межах часу життя кешу | Скидання кешу після кожного прогону парсера (`Ingestion Service` → `Cache Service`); абсолютний час життя запису — 15 хвилин |
| Безпека ↔ зручність діагностики (деталізація помилок) | Детальні повідомлення допомагають клієнту виправити запит, але тексти внутрішніх винятків розкривають будову системи: типи .NET, структуру моделей | Ризик розкриття інформації | `details` містить лише назву поля та людське повідомлення; винятки десеріалізатора приховано; повні деталі шукаємо в логах за `request_id` |
| Безпека ↔ сумісність (суворість валідації) | Суворі правила відхиляють дані, які раніше приймалися: наприклад, вакансію з 40 навичками | Парсер або старі клієнти можуть отримати 400 | Ліміти обрано з запасом відносно реальних вакансій; парсер нормалізує дані перед записом |
| Зручність ↔ прозорість (автовиправлення пагінації) | `page` менше 1 замінюється на 1, `pageSize` менше 1 — на 10, а більше 100 — на 100, замість відповіді 400 | Клієнт з помилкою отримує дані, але може не помітити, що просив 500 записів, а отримав 100 | Фактичні `page` і `pageSize` повертаються у відповіді; `page` понад 100 000 і далі відхиляється з 400, бо захищає від переповнення |
| Продуктивність ↔ обсяг даних за запит (пагінація) | Не більше 100 елементів на сторінку | Клієнту потрібно кілька запитів, щоб отримати все | Прапорці `hasNextPage` і `totalPages` у відповіді |
| Надійність ↔ затримка (таймаут LLM) | Довгий таймаут збільшує шанс дочекатися відповіді, але користувач довше чекає | До 30 с очікування | Індикатор очікування не пізніше ніж за 1 с (PERF-002) і перехід на звичайний пошук (REL-003) |

## 5. Як запустити перевірку

```bash
dotnet run --project src/api -p:TargetFrameworks=net10.0 --framework net10.0
```

Проєкти `waterfall.Services` і `waterfall.Repository` на Windows збираються ще й під Android, iOS і MAUI. Без встановлених навантажень MAUI звичайний `dotnet run --project src/api` завершується помилкою `NETSDK1147`, а параметри вище обмежують збірку платформою `net10.0`, як у CI на Linux. Під час першого запуску API створює файл SQLite `src/api/waterfall.db` і заповнює його демонстраційними даними.

Swagger UI: http://localhost:3000/api-docs. У кожній кінцевій точці натисніть **Try it out**, введіть дані з таблиці й порівняйте отриманий статус з очікуваним.

Два винятки з правила «невалідний вхід → 400» задає сама платформа ASP.NET Core, і вони очікувані:

- **id у шляху не є GUID** (`/vacancies/abc`): маршрут з обмеженням `{id:guid}` не збігається, тому відповідь — `404` без тіла у форматі помилок API.
- **Тіло надіслано не як JSON** (`Content-Type: text/plain`): відповідь — `415 Unsupported Media Type` у стандартному форматі ProblemDetails. Через Swagger UI цей випадок не відтворити, бо він завжди надсилає JSON.

## 7. Знайдені та виправлені проблеми валідації

Під час аналізу було знайдено випадки, коли невалідний запит проходив або завершувався 500, а валідний — відхилявся. Таблиця описує стан після злиття з PR #66, у якому моделі запитів перенесено в `waterfall.Services`:

| Запит | Було | Стало |
| --- | --- | --- |
| Порожнє тіло `POST`/`PUT` | **500**: фабрика помилок брала перший символ порожнього ключа ModelState | 400, поле `body` |
| `"source": "Djinni"` у тілі | **400 для валідного запиту**: під час перенесення моделей з `JobSource` зник конвертер рядкових перелічень, тож джерело приймалося лише числом, а у відповідях поверталося `3` замість `"Djinni"` | Джерело приймається й повертається назвою |
| `page=2147483647` | Переповнення `int` у `(page - 1) * pageSize`: на SQLite поверталася не та сторінка, а на SQL Server від'ємний OFFSET дає **500** | 400 |
| `POST /saved-vacancies` без `vacancyId` | 404 замість 400: `[Required]` не працює для `Guid`, і поле ставало `Guid.Empty` | 400 |
| `POST /vacancies` без `source` | Мовчки зберігалося `Unknown` | 400 |
| `"source": 99` у `PUT` | Зберігалося значення поза переліком | 400 |
| `salaryMin` > `salaryMax` у тілі або в query | Приймалося: перевірка зникла під час перенесення моделей | 400 |
| `search`, `category`, `experience` у query | Без обмеження довжини | До 100 символів |
| Будь-яка помилка в тілі запиту | До основної помилки додавався зайвий запис `request` з англійським «The request field is required.» | Лише помилки конкретних полів |
| Зламаний JSON або значення неправильного типу | Повідомлення містило назви типів .NET і номери рядків | «Некоректне значення або формат поля» без внутрішніх деталей |
| Довжина `description`, `sourceUrl` і кожної навички, кількість `skills` | Без обмежень | До 10 000, 2048 і 50 символів, до 30 навичок |
